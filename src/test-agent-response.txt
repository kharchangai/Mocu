بله، الان مسئله را می‌شود خیلی دقیق‌تر تعریف کرد. چیزی که می‌خواهی بسازی در اصل یک **File Retrieval Extension چندمرحله‌ای** است که وظیفه‌اش این نیست که پاسخ نهایی تولید کند؛ بلکه باید از میان فایل‌ها، **کوچک‌ترین بخش‌های مرتبط با درخواست کاربر را پیدا کند و با شماره‌خط برگرداند**.

معماری پیشنهادی:

```text
Agent Request
    ↓
Path and File Scope
    ↓
File Discovery
    ↓
Parsing and Line Metadata
    ↓
BM25 + Embedding Retrieval
    ↓
Candidate Selection
    ↓
JEV Relevance and Span Selection
    ↓
Context Expansion
    ↓
JSON Results with Line Ranges
```

---

# ۱. ورودی اکستنشن

اکستنشن بهتر است ورودی ساختاریافته دریافت کند، نه فقط یک متن آزاد.

مثلاً از نظر مفهومی:

```json
{
  "path": "E:/documents",
  "query": "اطلاعاتی درباره سهام شرکت اپل پیدا کن",
  "keywords": [
    "Apple",
    "AAPL",
    "stock",
    "shares"
  ],
  "fileTypes": [
    ".txt",
    ".md",
    ".pdf"
  ],
  "mode": "search",
  "maxResults": 10
}
```

برای جست‌وجوی کد:

```json
{
  "path": "E:/code",
  "query": "کدی برای ساخت embedding از فایل‌ها پیدا کن",
  "keywords": [
    "embedding",
    "vector",
    "chunk",
    "document"
  ],
  "fileTypes": [
    ".js",
    ".ts",
    ".py"
  ],
  "mode": "search"
}
```

## نقش فیلدها

### `path`

محدوده‌ی جست‌وجو را تعیین می‌کند. اکستنشن نباید خارج از این مسیر جست‌وجو کند، مگر اینکه صراحتاً اجازه داده شود.

### `query`

توضیح اصلی نیاز کاربر است و برای BM25، embedding و JEV استفاده می‌شود.

### `keywords`

کلمات مهمی هستند که ممکن است در متن وجود داشته باشند ولی در query اصلی نباشند. این کلمات برای جست‌وجوی lexical بسیار مفیدند.

### `fileTypes`

از جست‌وجوی فایل‌های غیرمرتبط جلوگیری می‌کند.

### `mode`

می‌تواند مشخص کند که اکستنشن فقط جست‌وجو کند یا مثلاً کد، مستندات، گزارش یا داده‌ی ساختاریافته را ترجیح دهد.

---

# ۲. مرحله‌ی پیدا کردن فایل‌ها

ابتدا باید فایل‌های موجود در مسیر پیدا شوند:

```text
Folder
 ├── report.txt
 ├── apple-analysis.md
 ├── old-data.json
 ├── image.png
 └── archive.zip
```

در این مرحله هنوز BM25 یا JEV لازم نیست.

اکستنشن باید:

- مسیر را بررسی کند
- فایل‌های مجاز را انتخاب کند
- فایل‌های مخفی یا سیستمی را در صورت نیاز کنار بگذارد
- حجم فایل را بررسی کند
- فایل‌های binary را تشخیص دهد
- اطلاعات پایه مثل نام فایل، نوع فایل و اندازه را نگه دارد

همچنین بهتر است نام فایل و مسیر فایل هم وارد ایندکس شوند؛ چون ممکن است query در محتوای فایل وجود نداشته باشد، اما نام فایل بسیار مرتبط باشد.

مثلاً:

```text
E:/documents/apple-stock-analysis.md
```

حتی اگر متن فایل کلمه‌ی `Apple` را کم داشته باشد، نام فایل سیگنال خوبی است.

---

# ۳. حفظ شماره‌خط‌ها از همان ابتدا

این بخش بسیار مهم است.

قبل از chunk کردن، هر فایل باید به خطوط دارای شناسه تبدیل شود:

```text
Line 1: Introduction
Line 2: Apple Inc. reported...
Line 3: Revenue increased...
Line 4: The stock price...
```

هر قطعه‌ای که بعداً ساخته می‌شود باید اطلاعات زیر را داشته باشد:

```text
documentId
filePath
startLine
endLine
text
```

مثلاً:

```json
{
  "documentId": "file-123",
  "path": "E:/documents/apple.md",
  "startLine": 20,
  "endLine": 38,
  "text": "..."
}
```

شماره‌خط باید مربوط به فایل اصلی باشد، نه شماره‌خط داخل chunk.

اگر یک chunk از خطوط ۲۰ تا ۳۸ ساخته شده، حتی اگر متن آن در ورودی JEV از خط ۱ شروع شود، باید به JEV اعلام شود که این خطوط در فایل اصلی از ۲۰ شروع می‌شوند.

---

# ۴. Chunk کردن نباید فقط بر اساس تعداد کاراکتر باشد

برای فایل‌های متنی، پاراگراف و heading معیارهای خوبی هستند.

برای کد، بهتر است chunk بر اساس ساختار زبان باشد:

```text
Function
Class
Method
Import block
Configuration block
Comment block
```

ساختار پیشنهادی:

```text
Document
 ├── Section
 │    ├── Paragraph
 │    └── Paragraph
 ├── Section
 │    └── Paragraph
 └── Section
```

برای کد:

```text
File
 ├── Imports
 ├── Class UserEmbedding
 │    ├── constructor
 │    ├── loadFile
 │    └── createEmbedding
 └── helper functions
```

هر chunk علاوه بر متن باید موقعیت اصلی خود را داشته باشد:

```json
{
  "chunkId": "file-123-function-createEmbedding",
  "type": "function",
  "startLine": 42,
  "endLine": 78
}
```

---

# ۵. چرا فقط BM25 کافی نیست؟

BM25 برای این نوع موارد بسیار خوب است:

```text
embedding
vector
chunk
Apple
stock
AAPL
```

اما ممکن است متن مرتبط از کلمات متفاوتی استفاده کند.

مثلاً query:

```text
کدی که متن فایل را به نمایش عددی تبدیل می‌کند
```

ولی متن فایل این باشد:

```text
Generate a dense representation from the input document.
```

از نظر مفهومی مرتبط است، ولی ممکن است اشتراک کلمه‌ی کمی با query داشته باشد. اینجا embedding کمک می‌کند.

پس پیشنهاد مناسب:

```text
BM25 = تطبیق کلمه‌ای و دقیق
Embedding = شباهت معنایی
JEV = قضاوت و انتخاب نهایی
```

نه اینکه JEV را جایگزین BM25 یا embedding کنی.

---

# ۶. معماری جست‌وجوی ترکیبی

مرحله‌ی retrieval بهتر است این‌گونه باشد:

```text
BM25 Search
    ├── Candidate A
    ├── Candidate B
    └── Candidate C

Embedding Search
    ├── Candidate B
    ├── Candidate D
    └── Candidate E

Merge and Deduplicate
    ↓
Candidate Pool
```

مثلاً:

- BM25 تعداد ۳۰ chunk پیدا می‌کند
- embedding نیز ۳۰ chunk پیدا می‌کند
- نتایج ترکیب و تکراری‌ها حذف می‌شوند
- نهایتاً ۲۰ تا ۴۰ candidate باقی می‌ماند

بعد این candidateها به JEV داده می‌شوند.

بهتر است JEV مستقیماً روی کل فایل‌های بزرگ اجرا نشود.

---

# ۷. راه‌حل متن‌های طولانی: جست‌وجوی سلسله‌مراتبی

مشکل اصلی تو دقیقاً این است:

> اگر فایل کوتاه باشد، می‌توان آن را کامل به JEV داد؛ اما اگر فایل طولانی باشد، ارسال کل فایل منطقی نیست.

راه‌حل مناسب **Hierarchical Retrieval** یا جست‌وجوی سلسله‌مراتبی است.

## مرحله‌ی اول: پیدا کردن بخش‌های بزرگ

فایل بزرگ را به بخش‌های نسبتاً بزرگ تقسیم کن:

```text
File
 ├── Block 1: lines 1-100
 ├── Block 2: lines 101-200
 ├── Block 3: lines 201-300
 └── Block 4: lines 301-400
```

روی این بخش‌ها BM25 و embedding اجرا می‌شود.

مثلاً فقط این بخش‌ها انتخاب می‌شوند:

```text
Block 2: lines 101-200
Block 4: lines 301-400
```

## مرحله‌ی دوم: تقسیم candidateهای بزرگ به بخش‌های کوچک‌تر

حالا فقط Block 2 و Block 4 را ریزتر کن:

```text
Block 2
 ├── lines 101-125
 ├── lines 126-150
 ├── lines 151-175
 └── lines 176-200
```

دوباره retrieval انجام بده و بخش‌های محتمل را انتخاب کن.

## مرحله‌ی سوم: ارسال بخش‌های کوچک به JEV

در نهایت JEV فقط candidateهای کوچک را می‌بیند:

```text
lines 126-150
lines 176-200
lines 325-350
```

این کار باعث می‌شود JEV به جای خواندن ۱۰ هزار خط، فقط چند بخش محدود را بررسی کند.

---

# ۸. چه زمانی فایل کامل به JEV داده شود؟

یک قانون ساده داشته باش:

```text
فایل کوتاه → کل فایل
فایل متوسط → بخش‌های بزرگ
فایل بلند → retrieval سلسله‌مراتبی
```

اما معیار نباید فقط تعداد خط باشد. حجم توکن هم مهم است.

مثلاً:

```text
اگر متن کمتر از حد مشخصی بود:
    کل متن را به JEV بده

اگر بزرگ‌تر بود:
    ابتدا به block تقسیم کن

اگر خیلی بزرگ بود:
    ابتدا BM25 و embedding را روی blockها اجرا کن
```

برای فایل‌های کد، حتی اگر تعداد خطوط کم باشد، ممکن است هر خط بسیار طولانی باشد. بنابراین اندازه باید با token یا طول متن نیز کنترل شود.

---

# ۹. نقش دقیق JEV

JEV نباید اولین موتور جست‌وجو باشد. وظیفه‌ی اصلی آن بعد از retrieval این است:

1. تشخیص دهد candidate واقعاً مرتبط است یا نه
2. میزان ارتباط را تعیین کند
3. بخش‌های مهم داخل candidate را مشخص کند
4. شماره‌خط‌های مهم را برگرداند
5. بخش‌های ناقص را با اطرافشان گسترش دهد
6. بین چند candidate انتخاب کند

ورودی JEV بهتر است شامل این موارد باشد:

```text
User request
Keywords
Candidate ID
Original line numbers
Candidate text
```

برای جلوگیری از اشتباه در شماره‌خط، متن را به شکل شماره‌گذاری‌شده به JEV بده:

```text
[Line 126] The embedding model receives...
[Line 127] The document is split into chunks...
[Line 128] Each chunk is converted into a vector...
```

از JEV بخواه:

- آیا این candidate به درخواست مرتبط است؟
- کدام خطوط مستقیماً مربوط هستند؟
- آیا خطوط اطراف برای فهم کامل لازم‌اند؟
- آیا این بخش پاسخ کافی دارد یا فقط اشاره‌ی سطحی است؟

خروجی مفهومی JEV:

```json
{
  "relevant": true,
  "confidence": 0.91,
  "importantLineRanges": [
    {
      "startLine": 126,
      "endLine": 134,
      "reason": "این بخش روند ساخت embedding را توضیح می‌دهد."
    }
  ],
  "needsNeighboringLines": true
}
```

---

# ۱۰. پیدا کردن خط‌های مهم داخل یک chunk

فرض کن retrieval یک chunk از خطوط ۱۰۰ تا ۲۰۰ پیدا کرده است. این chunk هنوز برای خروجی بزرگ است.

JEV باید بتواند از داخل آن، spanهای مهم را انتخاب کند:

```text
Candidate: lines 100-200
    ↓
JEV
    ↓
Relevant spans:
- lines 112-121
- lines 148-157
```

بنابراین لازم نیست خروجی اکستنشن کل chunk باشد. می‌تواند فقط بخش‌های مهم را برگرداند.

اما یک نکته مهم وجود دارد:

## JEV نباید شماره‌خط را از خودش حدس بزند

شماره‌خط‌ها باید داخل ورودی به صورت صریح وجود داشته باشند. مثلاً:

```text
[Original line 112] ...
[Original line 113] ...
```

در این صورت JEV فقط از بین شناسه‌های موجود انتخاب می‌کند.

بهتر است به جای درخواست شماره‌خط آزاد، از آن بخواهی یکی از line IDهای داده‌شده را انتخاب کند. این کار خطای شماره‌گذاری را کاهش می‌دهد.

---

# ۱۱. Context Expansion

گاهی JEV یک خط را مهم تشخیص می‌دهد، ولی آن خط به‌تنهایی معنای کاملی ندارد:

```text
Line 210: It should be passed to the encoder.
```

اگر فقط خط ۲۱۰ را برگردانی، معلوم نیست `It` به چه چیزی اشاره می‌کند.

پس بعد از انتخاب span باید یک مرحله‌ی گسترش context وجود داشته باشد:

```text
JEV selected: line 210
    ↓
Extension adds neighboring lines
    ↓
Return lines 206-214
```

این گسترش می‌تواند بر اساس نوع فایل متفاوت باشد:

### متن عادی

چند خط قبل و بعد یا کل پاراگراف.

### Markdown

کل heading مربوط و پاراگراف‌های زیر آن.

### کد

کل تابع، متد یا کلاس مربوط.

### JSON/YAML

کل object یا array مربوط.

بنابراین خروجی نهایی لزوماً دقیقاً همان line range خام انتخاب‌شده توسط JEV نیست؛ ممکن است برای حفظ معنا کمی بزرگ‌تر شود.

---

# ۱۲. دو سطح انتخاب با JEV

بهتر است JEV را در دو نقش جدا ببینی.

## JEV اول: انتخاب candidate

از بین candidateهایی که BM25 و embedding پیدا کرده‌اند:

```text
کدام بخش‌ها واقعاً به query مربوط هستند؟
```

خروجی:

```text
candidate-2
candidate-7
candidate-9
```

## JEV دوم: انتخاب span

داخل candidateهای انتخاب‌شده:

```text
کدام خطوط مهم هستند و باید به Agent برگردند؟
```

خروجی:

```text
candidate-2 → lines 45-57
candidate-7 → lines 201-220
```

این دو مرحله را می‌توان برای کاهش هزینه در بعضی موارد ترکیب کرد، ولی از نظر معماری جدا بودنشان بهتر است.

---

# ۱۳. خروجی نهایی اکستنشن

خروجی باید علاوه بر متن، metadata کافی داشته باشد:

```json
{
  "query": "کدی برای ساخت embedding از فایل پیدا کن",
  "results": [
    {
      "filePath": "E:/code/embedding.ts",
      "fileName": "embedding.ts",
      "fileType": "typescript",
      "startLine": 42,
      "endLine": 68,
      "text": "...",
      "relevanceScore": 0.94,
      "source": {
        "bm25": 0.81,
        "embedding": 0.92,
        "jev": 0.95
      },
      "reason": "این تابع متن فایل را chunk کرده و برای هر بخش embedding می‌سازد.",
      "contextExpanded": true
    }
  ]
}
```

برای یک فایل ممکن است چند نتیجه وجود داشته باشد:

```json
{
  "filePath": "E:/documents/apple-report.md",
  "matches": [
    {
      "startLine": 32,
      "endLine": 47,
      "text": "..."
    },
    {
      "startLine": 91,
      "endLine": 108,
      "text": "..."
    }
  ]
}
```

بهتر است نتایج بر اساس فایل گروه‌بندی شوند، اما هر match line range مستقل داشته باشد.

# ۱۵. نکته مهم درباره‌ی embedding

Embedding نباید الزاماً روی کل فایل ساخته شود. بهتر است چند نوع embedding داشته باشی:

```text
File-level embedding
Section-level embedding
Chunk-level embedding
```

اما برای نسخه‌ی اولیه:

```text
Chunk-level embedding
```

کافی است.

برای فایل خیلی بزرگ، embedding بخش‌های بزرگ‌تر کمک می‌کند ابتدا محدوده‌ی مناسب پیدا شود. سپس روی آن محدوده‌ها به chunkهای کوچک‌تر بروی.

همچنین برای کد، embedding نام تابع، نام کلاس و commentها را هم در متن ورودی embedding قرار بده؛ چون این metadata معمولاً اطلاعات مفیدی درباره‌ی کاربرد کد می‌دهد.

---

# ۱۶. چه چیزی را فعلاً نسازی؟

برای MVP لازم نیست از ابتدا این قابلیت‌ها را بسازی:

- تولید پاسخ نهایی توسط LLM
- خلاصه‌سازی کل فایل
- جست‌وجوی خودکار در کل سیستم
- چندین مدل embedding
- تصمیم‌گیری پیچیده درباره‌ی نوع خروجی
- پردازش هم‌زمان همه‌ی فرمت‌ها

نسخه‌ی ابتدایی می‌تواند این باشد:

```text
1. دریافت path و query
2. خواندن فایل‌های متنی و کد
3. حفظ شماره‌خط
4. ساخت chunk
5. BM25
6. embedding برای candidateها
7. JEV برای انتخاب candidate و line span
8. برگرداندن JSON
```

---

# جمع‌بندی نهایی

معماری مناسب برای چیزی که می‌خواهی این است:

```text
BM25 و Embedding
    برای پیدا کردن بخش‌های احتمالی

JEV
    برای تشخیص ارتباط واقعی و انتخاب خطوط مهم

Context Expansion
    برای کامل کردن بخش انتخاب‌شده

JSON Output
    برای تحویل متن، مسیر فایل و شماره‌خط به Agent
```

برای متن‌های بلند هم نباید کل متن را به JEV بدهی و نباید کورکورانه هر بخش را جداگانه بررسی کنی. باید از این روش استفاده کنی:

```text
فایل بزرگ
  ↓
Blockهای بزرگ
  ↓
BM25 + Embedding
  ↓
Blockهای مرتبط
  ↓
Chunkهای کوچک‌تر
  ↓
JEV
  ↓
Spanهای مهم با شماره‌خط
  ↓
گسترش context
  ↓
خروجی JSON
```

در این معماری، اکستنشن فقط **اطلاعات مرتبط و قابل استناد** را تحویل Agent می‌دهد؛ تصمیم‌گیری درباره‌ی پاسخ نهایی همچنان بر عهده‌ی Agent باقی می‌ماند.
